# my-ai-team-docs operator guide

This repository is the public publication target for the my-ai-team
documentation site at <https://mat-docs.shukelabs.com/>. It contains only the
curated public docs, the Astro/Starlight site, build verification, and the
metadata needed to publish them. The product source and private repository
history are not part of this checkout.

The docs and site materials are licensed under [CC BY 4.0](./LICENSE-DOCS).

## Public boundary

The tracked publication inputs are deliberately small:

- `docs/public/*.md` contains the customer-facing pages.
- `CHANGELOG.md` is a sanitized public release-history snapshot.
- `examples/mat/backends.json` and `examples/mat/user.conf` are the public
  configuration examples.
- The first product paragraph in the root `README.md`, before `## Install`,
  supplies the overview page.
- `.docs-version` states the published release version.
- `docs-site/` contains the site implementation, manifest, tests, lockfile,
  and this operator guide.

The repository must not receive private product source, agent prompts, internal
documentation, credentials, or private Git history. The exclusion inventory in
`content-manifest.mjs` is retained as guard metadata: it supplies the forbidden
names and path prefixes used to verify the rendered boundary, not additional
content for publication.

## Projection contract

The private repository remains the source of truth during phase one. Everything
in this repository except the two owned paths listed below is **generated by a
one-way projection** and will be overwritten by the next run, so a fix belongs
in the private source, not here.

The projection materializes:

1. The approved Markdown pages under `docs/public/`, taken from the private
   repository's published-page allowlist — the same allowlist the site build and
   the leak guard read, so a new customer page arrives with no contract edit.
2. A sanitized generated `CHANGELOG.md`: internal issue/PR references, internal
   document names, and internal source paths are removed before commit.
3. The two approved configuration examples.
4. The root `README.md`, generated from the private product overview with the
   `## Install` boundary the overview sync reads, so the published overview page
   cannot drift from the product framing.
5. `.docs-version`, the validated `vX.Y.Z` release version. The site resolver
   prefers it over a Git tag, which is what gives this tag-less checkout a real
   release badge. A `DOCS_VERSION` environment override still wins over both,
   and any value that is not `vX.Y.Z` fails the build rather than degrading.
6. The site implementation, manifest, licence, unit suite, and build
   configuration under `docs-site/`.

One target prefix is **owned by this repository** and is never written or
deleted by a projection run: `.github/**`, the hosted-runner verification and
deploy workflow. Everything else is projected, `docs-site/test/` included — the
unit suite travels with the site code it tests, so a projected change can never
leave this repository with a suite that fails on it. Two suites in the private
source are the exception and never arrive here, because each imports a private
tool that is not projected: the projection's own contract suite and the
publication-confirmation suite. The tests present in this repository are
therefore the complete suite for the site code it holds.

Before publishing, the projection scans every projected content file with the
site's own leak-guard rules and refuses to publish on any hit, so internal
document names, internal source paths, `#`-number references to the private
tracker, and proprietary markers cannot reach this repository. The build-time
sanitizer and `scripts/leak-guard.mjs` remain the final fail-closed checks.
A new public page still needs a deliberate sidebar entry in `astro.config.mjs`.

### Update trigger

After cutover, the private repository's trusted projection workflow runs after
each successful Release completion. It checks out the trusted `main` tip so the
generated changelog and `.docs-version` are projected together. Nothing in this
repository pulls from the private source, and no workflow here holds a private
source credential. Each projection updates the single `projection/public-docs`
branch, opens or refreshes one pull request, waits for this repository's
required `verify` check, and squash-merges it. A no-op run creates nothing.

The private repository stores the projection App's `APP_ID` and
`APP_PRIVATE_KEY`; the App installation is limited to this repository and has
contents plus pull-request write/merge access. Its short-lived token is used
only by the trusted projection job, never by pull-request verification. This
repository stores only the Cloudflare deploy secrets used by its protected-main
deploy job, and those secrets are never available to fork pull requests.

### Failure handling

A projection run is fail-closed and never publishes a partial tree. It aborts,
with no partial tree, no branch, and no pull request created, when a source is
missing or unreadable, when the resolved version is not a real release, when the
generated overview cannot be derived, when the boundary scan finds anything the
public boundary rejects, or when the source revision has not yet reached the
private default branch — only reviewed documentation is published here.

A clone, commit, or push failure reaches this repository with nothing. A
pull-request, verification, or merge failure leaves the generated
`projection/public-docs` branch while `main` and the deployed site remain
untouched; the next trusted run refreshes that branch and retries the same PR.
In every case the previously published projection remains current, so a failed
run degrades to "not updated yet", never to a half-updated site.

The private workflow fails closed before pushing when its runner lacks the
projection toolchain, when it cannot recover the machine-readable projection PR
URL, or when the public `verify` context does not register within its bounded
wait. A red public check is never treated as a successful publication.

### Rollback and retry

- **Retry.** Fix the private source and run the projection again. A rerun
  refreshes the single generated branch and pull request; a rerun that finds
  nothing changed is a no-op, so retrying is always safe.
- **Rollback.** Revert the projection pull request on `main`. The revert
  redeploys the previous tree through the normal deploy job. Do not hand-edit
  projected files to undo a change: the next run would restore it. Roll the
  private source back too, or the following run will republish the reverted
  content.
- **Superseded pull request.** There is normally no older projection pull
  request because the generated branch is reused. If one is stranded, close it
  and let the next trusted run recreate it from `projection/public-docs`.

## Local development

```bash
cd docs-site
pnpm install
pnpm run dev
pnpm run build
pnpm run leak-guard:self-test
```

Requires Node 20+ and pnpm 11.11.0, as pinned by `package.json`; CI uses Node
22.19.0. The frozen
`pnpm-lock.yaml` and `pnpm-workspace.yaml` keep installation reproducible and
approve only the required dependency build step.

The version badge comes from `.docs-version`, so a plain checkout with no tags
fetched still renders a stable release version. `DOCS_VERSION` overrides it for
a one-off build and must itself match `vX.Y.Z`; invalid overrides fail the
build.

## Verification and deployment

`.github/workflows/docs-deploy.yml` is maintained in this repository and has no
path filters: every pull request and
every push to `main` runs on `ubuntu-latest` and performs dependency
installation, the high-severity dependency audit, unit tests, the Astro build,
the postbuild leak guard, and the leak-guard self-test. Checkout uses full
history and tags (`fetch-depth: 0`, `fetch-tags: true`).

The deploy job runs only after verification succeeds and only for a push to the
trusted default branch `main` — a `workflow_dispatch` run therefore verifies
without deploying, and recovering a failed deployment means re-running the
failed push run rather than dispatching a new one. It installs the same frozen dependency tree as
verification — `cloudflare/wrangler-action@v3` resolves its package manager
from `docs-site/package.json`, so the deploy job needs Node and pnpm too — and
uploads `dist` to the existing Cloudflare Pages project `mat-docs`, preserving
`mat-docs.shukelabs.com`. It requires both repository secrets and fails with an
explicit message when either is absent, so a credential regression cannot look
like a successful publication:

- `CLOUDFLARE_API_TOKEN` with Pages Edit permission.
- `CLOUDFLARE_ACCOUNT_ID` for the Pages account.

Those secrets are scoped to the deploy job, which is not created for fork pull
requests. Forks receive verification only and cannot receive deployment
credentials.

This protected-main workflow is the sole production publisher. If a public
build or deploy fails, the previously deployed revision remains current until
the projection is fixed or the workflow is re-run; the update that carried it
is reported as failed rather than published.
